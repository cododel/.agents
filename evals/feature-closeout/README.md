# Evaluate feature closeout

See the [observed migration results](results.md) for the matched runs, limitations and costs.

The seven original Engineering Review v0.1.0 fixtures, protocol, previously reported checks and evaluator-only oracle are preserved in `upstream/`. Their original case directory names and oracle reveal intended outcomes. Give reviewers only the neutral materialized packet, assigned skill (without evals), shared policies and established adjacent owners. The original validation note describes packaging checks performed for v0.1.0.

1. Before any run, save exact copies/digests of A (pre-change Feature Closeout), B (Engineering Review v0.1.0) and C (candidate Feature Closeout), current common rules and shared owner skills. Freeze the inputs, `grading.md` and `upstream/oracle.md`. Do not change the grader to fit results. Keep graders, runner scripts, this directory, prior reports and other arms out of reviewer context. Do not use a full-history conversation fork. In a shared filesystem restrict each context explicitly to its packet and assigned policy/skill tree and disclose the isolation boundary.
2. Run `python3 prepare.py portfolio <new-scratch-path>` once per arm and repetition, with a neutral destination name. The eight components have the same baseline, candidate, specification and fixed order in each arm. `REQUEST.md` is the common instruction. Only the assigned method differs. Do not expose source fixture paths. Use consistent model/version, effort, local tools, credentials policy, independence availability and time/tool budget. Verify packet digests match before starting. For each arm capture immutable response, actual calls, artifact copies and candidate digests. For a less context-sensitive replication materialize and review one component per fresh context using the original protocol.
3. Compare authorized repair separately using `repair` and fresh writable targets. For independent read-only checks use `small`, `checkpoint`, `frozen`, `release`, `drift`, `limits` and `independence`. Each generates an independent packet and user request. The release and required-independence trials simulate an unavailable independent reviewer, while frozen resumes an already-returned independent review. For read-only trials verify actual candidate bytes remained identical. An eval runner may provision a dedicated artifact/scratch path without granting product write authority.
4. Freeze all replies before scoring. Hide arm labels from graders where practical. Use the two scorecards, and retain per-arm observations even for failures, abstentions and timeouts. Keep the existing repository regression probes (including the two-sample comparison in `../behavior-probes.md`) alongside this evaluation. Repeat at least twice per arm, preferably three when practical. Record missing runs individually and distinguish a smoke sample from a completed replicated comparison.

All packet data are synthetic, and the inputs use Python's standard library or static JS. No provider, package install or remote environment is necessary. The portfolio is a comparative discovery exercise. A successful fixture or packaging check alone supplies no evidence of agent behavior.

After a repair trial, run the held-out evaluator probe in a separate process with
`python3 -B check_fulfillment.py <packet>/fulfillment/candidate`. It checks the happy path,
pause/resume, three readiness mismatches, diagnostic confidentiality and transport retry without
emitting the synthetic locator. Run it only on disposable trusted fixture code. On the supplied
baseline all seven observations pass. On the as-supplied candidate only delivery and retry pass.

The remaining existing closeout behavior probes have individual neutral workspaces generated by
`prepare_regressions.py`; the case list, batching guidance and expected outcomes are in the
evaluator-only [continuity scorecard](regression-grading.md).
