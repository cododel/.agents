# Evidence for reports and change reviews

Select each artifact for the specific claim it actually establishes. Do not carry attachments
forward merely because they appeared in an earlier report or Issue. Caption the demonstrated result,
relevant version/environment and confirmation limits. Omit noncontributing material; retain context
only when it helps the reader and label it as context, not proof.

Use screenshots for visible state claims. A normal-looking state alone does not establish a preceding
action, transition or wrong input owner. Use video when the sequence or dynamics are material, showing
the relevant actions and observed outcome against the stated expectation. Still images cannot prove
unrecorded interactions. Logs, tests and other inspectable records support only their exercised or
recorded boundaries. Avoid redundant artifacts; no screenshot-plus-video pair is automatically required.

For a user-visible change, demonstrate the relevant resulting behavior with evidence suited to its
claim. Nonvisual changes can use meaningful test results, output or other inspectable records; do not
add decorative media. A new feature need not be framed as an old defect. Preserve applicable gaps
explicitly rather than fabricate a demonstration or expand investigation beyond task authority.
Use [testing-evidence](../testing-evidence/SKILL.md) for substantive verification design or interpretation.

Exclude secrets, personal data and unrelated workspace content while preserving decisive diagnostics;
use synthetic examples where possible. Use new filenames for changed evidence so existing review
comments do not silently refer to different content. Before authorized publication,
resolve attachment locations for the recipient and keep the canonical Markdown synchronized. Local
preview paths are not publicly accessible uploads; media preparation grants no upload authority.
