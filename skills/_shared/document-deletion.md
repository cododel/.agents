# Document deletion

Use only for a proposed document deletion, after the owning workflow has established its scope,
value/lifecycle criteria and required authority. This procedure does not choose documents for removal
or override scenario-specific requirements. Reuse existing evidence and reporting; no new record
format or separate audit is required.

## Value and references

Read the candidate in full. Unresolved value, lifecycle, scope or required checks block deletion.
Unique knowledge must already have a verified appropriate owner; recovery from Git is not a substitute
for preserving knowledge still needed by consumers. A safe evidence result grants no mutation authority.

Search the confirmed repository for the exact filename/path, slug and distinctive decision/problem
identifiers, excluding generated/dependency trees and the candidate. Trace actual links rather than
assuming every text match is load-bearing. A semantic reference stays blocking until its meaning has
a verified owner and its link is repaired. An unambiguous index-only entry may be removed or redirected
in the same change, followed by recheck. Unknown reference meaning, incomplete search or ambiguous
repair keeps the source. Reuse a completed applicable search rather than repeating it mechanically.

## Recovery and target validity

Resolve the exact canonical path, require a regular non-symlink file within the confirmed scope, and
record its content fingerprint. A symlink, path escape, invalid/changed type or unresolved scope is
blocked until corrected and rechecked; approval cannot bypass target validity or incomplete evidence.

Recovery is proven only when Git tracks the exact path, working-tree and index contents are clean
and match the current bytes in a reachable commit. Record that commit SHA and repository-relative
path. An old committed version does not prove recovery of modified current contents.

Valid untracked, staged/modified, ignored-only or otherwise unproven contents require an exact-path
recovery checkpoint; an unverified backup does not establish recovery. Never stage or commit a source
merely to satisfy this check. Backlink/extraction edits invalidate dependent recovery evidence and
require reassessment of current contents, distinct from the committed version.

## Authority

Review/audit mode remains read-only regardless of recovery. In apply mode, exact recoverable files
may be deleted without renewed approval only when the existing request covers the action and scope
and the owning workflow's additional conditions are satisfied.

For valid targets with unproven recovery, present the exact paths, fingerprints/state, reason and safer
alternative for the operator's choice. Reuse explicit authorization covering that same state; do not
ask again merely because this procedure is loaded. Bulk approval covers only the already shown exact
list while its state and circumstances remain unchanged, never unseen paths. No recovery approval
can bypass unresolved value, required provenance or scenario-specific semantic authority.

## Apply and verify

Immediately before each authorized deletion:

1. Re-resolve path/type/scope, re-read the source and recompute its fingerprint and Git state.
2. Recheck decisive lifecycle/value/reference evidence and the owning workflow's prerequisites.
3. Skip that path on drift; reconcile changed evidence or authority before reconsidering it.
4. Apply planned unambiguous index/link repairs and remove the exact file in the same change.
5. Recheck repaired/remaining incoming references. If repair fails, restore only this task's exact
   deletion and retain/report the source.

Never use a broad glob or recursive directory delete. Staging/committing and external/shared actions
retain their separate authority requirements. Report actual retained/deleted/gated/blocked or
changed-state outcomes through the owning workflow, without claiming unperformed checks succeeded.
