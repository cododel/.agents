# Cododel Post Covers

Create a cover that identifies the post at a glance. The operator explicitly adopted the retained
example as his signature cover style. Use [the approved SVG](assets/approved-cover.svg) as an
editable composition reference and inspect [its PNG](assets/approved-cover.png) before authoring.
These are a cover example, not instructions to reuse its topic or document icon for every post.

## Visual language

- Pure black background `#000000`, white headline, one Electric Blue accent `#2663EB`. Neutral
  greys for quiet lines and secondary branding. No extra accent palette, gradients, textures,
  rendered 3D objects or decorative shadows.
- Large, bold uppercase headline with tight spacing. The accepted Cyrillic reference uses Arial;
  metadata and the short topic/tool label use Menlo or an available comparable monospace face.
  Check actual Cyrillic glyphs and rendered widths; do not promise unavailable brand fonts.
- Sharp rectangular containers and thin structural rules. Preserve the blue top strip, restrained
  `CODODEL ///` masthead and `cododel.dev` signature. Adapt the masthead's topic suffix when useful;
  `.AGENTS` belongs to this example, not every future subject.
- Minimal copy: a short headline, optional short tool/topic label, small branding. No explanatory
  paragraph, mandatory subtitle, numbered steps, multi-node flow, legend or checklist.
- One simple topic-related vector motif with generous negative space. The example's document,
  highlighted patch and return arrow fit skill evolution. Choose an equally simple relevant motif
  for a different topic; do not turn it into a process diagram.

## Make the cover

1. Read the supplied post or brief and identify its actual subject. Reuse a supplied headline when
   requested; otherwise write a short concrete one without inventing facts or a dramatic claim.
   Ask only if missing material prevents choosing the subject. Do not rewrite the post itself.
2. Start from a copy of the approved SVG in the authorized output workspace. Default to the accepted
   landscape format, `1600 × 1000` logical units; the reference PNG is `3200 × 2000`. Follow an
   explicit requested output size instead. Preserve the visual language when adapting the layout.
3. Fit the headline and the motif as separate visual areas. In the reference, text starts around
   x=80, the main motif around x=1130, and the exterior margin is about 5%. Recompose or shorten a
   long headline within its meaning before letting it collide, clip or become tiny. Exact geometry
   is an example, not a universal constraint on other aspect ratios.
4. Author the graphic directly as SVG; no ImageGen or other raster-generation service by default.
   Keep its content editable. Use an existing local SVG renderer or available browser export to
   produce PNG. Discover available runtimes/libraries; do not hardcode machine-specific paths or
   install a new renderer/dependency without authorization. If PNG rendering is unavailable, retain
   the SVG and state the missing export step rather than claim a rendered deliverable.
5. Inspect the actual PNG for text accuracy, glyphs, clipping, headline/motif separation and balance
   at a small phone-preview size. Confirm the correct subject and that the result is a cover, not
   a compressed infographic. Fix clear layout defects before delivery.
6. Return the image inline with usable PNG and SVG links. Save outputs as new files unless replacing
   the exact output is requested. Do not overwrite this package's approved reference while making
   an ordinary cover. Publication, commits and pushes retain their own authorization boundaries.

## Evolution

The maintained learning surface is this package's entrypoint, target-owned references and assets.
Its evolution loop is embedded here; future cover generation does not require a meta-skill, wiki
access or the originating chat.

Finish the current cover first when operator feedback, a reproducible rendering problem or a new
requested type reveals a gap. Distinguish a one-cover edit from a reusable style refinement, a
technical defect and a new format. Keep only the minimum confirming instruction, scoped failure
or accepted before/after example; do not capture whole conversations or unaccepted drafts.

- **Technical repair:** reproduce the defect and verify the fix on the affected case, one different
  headline and the approved baseline. Apply a narrow source repair only within existing write
  authority; otherwise prepare a candidate outside active instructions.
- **Style refinement or new type:** apply current-task direction to the requested cover. Prepare a
  minimal candidate for the package, specifying scope, evidence, a case where it should not apply
  and what stays invariant. Persist only after operator approval covering that rule/type. An explicit
  instruction to save the exact refinement supplies it; do not ask again for the same authority.
  Approval of one image alone does not make every incidental detail a permanent style rule.
- **Evolution policy or permissions:** require an explicit external decision. This loop cannot
  change its own evidence standard, write surface or approval requirements.

For an approved new type, add a target-owned layout reference only when it has distinct reusable
requirements; route to it from this entrypoint. Preserve the original cover type and its accepted
reference unless explicitly superseded. Do not invent types in advance or create near-duplicate
skills for aspect ratios. Unknown image acceptance and agent aesthetic preference are not evidence
of a better brand rule.

Before promoting a candidate, render the changed case and a new transfer example; check the old
landscape baseline, short-copy budget, palette and separation of text from motif. Mechanical
rendering proves layout properties, not subjective preference: obtain external assessment for the
new design. Keep the exact diff/version or an authorized before-copy for a scoped undo. Disclose
what was learned, what changed versus remains proposed, actual checks and limits. Revisit rules
when contradicted; revise their owner instead of accumulating a diary or conflicting instructions.
