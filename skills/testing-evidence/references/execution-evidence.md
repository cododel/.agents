# Execution, Final Gates And Result Identity

Resolve the project profile, affected radius and real service targets before execution. Local paths
or localhost do not establish disposable DB/API targets. Use established isolated test harnesses;
production/shared data actions follow global authorization policy. Inspect collection/setup/build
side effects as well as the command name. Do not install a new runner or cache to satisfy this skill.

## Iterations and final evidence

Start with the smallest check that distinguishes the intended behavior. Add relevant static/type/
build checks and affected integration/consumer checks. Full suites are final/integration evidence by
project policy or affected risk, not an automatic checkpoint ritual. Required project gates remain
required; disclose unavailable parts rather than substitute narrower evidence.

The canonical final set is a set of evidence obligations, not another executable gate. Deduplicate
overlapping runs: an appropriate current broader result may satisfy its covered focused checks.
Keep serial/order variants for import/global-state pollution, non-UTC variants for conversion, and
cross-OS/process/filesystem variants where behavior differs. Identical assertions do not make these
equivalent. Runtime/skip/duration claims require observed execution, not collection or source labels.

## Reuse and invalidation

Reuse depends on compatible **code + deps + config + environment + selection**. Include relevant dirty
bytes, lock/dependency versions, harness/plugins, platform/runtime/backend, service/schema state and
effective filters/flags (`PYTEST_ADDOPTS`, paths, markers, `-k`, exclusions). HEAD alone is insufficient.
Record only material facts, not secrets/full env dumps; a concise command/result explanation suffices
for small work. Prove exact selection or that the successful superset includes required cases.

Invalidate only dependent evidence after changes or failures; preserve demonstrably independent
results. Unknown relevance makes reuse unverified. A later failure for the same guarantee/selection
supersedes old green. Diagnose and repair/recheck or disclose the blocker; do not resurrect green from
memo. After fixing code refresh source identity and affected final evidence.

Cache/wrapper success is evidence only to the extent its identity/invalidation contract holds. A
force-failed command retaining an old success memo cannot certify current success. A command named
"full" with `PYTEST_ADDOPTS=-k subset` cannot certify full coverage even when exit code is zero.
When a wrapper's scope is untrustworthy, inspect actual selection and obtain direct appropriate
evidence or report not-run/failed; repairing its implementation requires its own authorized scope.

## Outcomes and claims

For each material check or set distinguish:

- **passed**: actual selected check completed successfully at the claimed boundary.
- **failed**: selected check failed; classify product versus setup/environment/pre-existing failure.
- **skipped**: selected check was skipped by harness/condition; never count as passed proof.
- **not-run**: check not executed, including unavailable required platform/service.

For mixed sets report components/counts and selection, rather than hide skips under "all green".
Collection exit zero, empty selection, fake outcome, historical aggregate, static counterfactual or
passing lint cannot be promoted into a different kind of proof. Separate observations, conclusions
and assumptions; compare evidence with every material acceptance criterion and disclose gaps.
